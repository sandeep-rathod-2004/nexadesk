# Architecture

Current local flow: React browser UI → FastAPI authentication and tenant-scoped API → SQLAlchemy session → SQLite (default) or PostgreSQL → AI provider interface (Ollama or Gemini) → streamed and persisted response.

The browser does not call Ollama directly. Provider configuration stays on the backend.

Authenticated `GET /api/v1/model` reports the configured provider and model so the UI can identify the active model without hardcoding it. Chat completions continue to include the actual model name. Assistant messages render Markdown with GitHub-flavored tables and syntax-highlighted code; raw HTML is disabled and links are restricted to safe schemes.

Registration creates a user, workspace, and owner membership. JWT bearer tokens authenticate protected API calls. Conversations and messages are persisted; access requires both membership in the conversation workspace and ownership by the authenticated user. Workspace owners can add existing registered users as members.

The authenticated conversation resource supports list/create/retrieve, `PATCH /api/v1/conversations/{conversation_id}` for rename, `DELETE /api/v1/conversations/{conversation_id}` for deletion, and `GET /api/v1/conversations/{conversation_id}/messages` for message history. Every ID-based operation verifies the current user's workspace membership and conversation ownership on the backend.

`POST /api/v1/chat/stream` streams tokens from the configured provider using Server-Sent Events. Send a UUID `request_id` in the JSON body and reuse it when retrying the same message: completed requests replay the saved response, while conflicting or currently processing requests return `409`. SSE events are `token`, `complete`, and `error`; the final event includes RAG source references. User and assistant messages are persisted together only after a complete provider response, and disconnects cancel the provider stream and release the pending request. Token activity refreshes the idempotency lease so abandoned reservations can be retried after a server crash. The authenticated non-streaming `POST /api/v1/chat` remains available.

Database schema changes are managed through Alembic. Run `alembic upgrade head` from `backend/` only against the intended database before starting the API. `DATABASE_URL` configures the SQLAlchemy connection; SQLite remains the local default, and PostgreSQL URLs use psycopg 3. Existing migrations use SQLAlchemy UUID/JSON types, portable constraints/indexes, and server defaults; Alembic enables batch mode for SQLite. In development, an omitted JWT secret is generated randomly for the process; configure `JWT_SECRET_KEY` to retain tokens across restarts. Production mode requires a configured JWT secret.

AI chat and embeddings use backend-selected provider interfaces (`AI_PROVIDER` and `EMBEDDING_PROVIDER`). Ollama and Gemini Developer API adapters are implemented and selected independently; Gemini uses the official `google-genai` SDK and a backend-only API key. Model prompts retain the shared system/RAG instructions, stream response text progressively, and map provider failures to safe service errors. Transient failures use a bounded retry count, rate limits are surfaced explicitly, and streaming is not retried after response text has been emitted. Provider/model usage metadata is retained by the adapter where available without logging prompt or response contents. There is no automatic provider fallback.

Embedding documents record provider, model and vector dimension. Retrieval checks these values and refuses known-incompatible indexes. The first migration leaves legacy embedding identities null because the originally used model cannot be determined from stored vectors. Such indexes remain backward-compatible with Ollama, but must be re-ingested before using Gemini embeddings; re-index after any provider/model/dimension change. Changing only the chat provider does not change embedding identity. Gemini free-tier data handling may allow content to be used to improve Google's products; do not submit confidential customer data or private documents to that tier. API credentials remain backend-only, and no billing is enabled by the application.

Knowledge documents use a storage interface for upload, seekable reads, deletion, existence and metadata. The local filesystem adapter remains the default. The Cloudflare R2 adapter uses the private S3-compatible API, backend credentials, generated workspace-prefixed object keys, bounded SDK retries and timeouts. Uploads are staged in a spooled temporary file, so larger payloads spill to disk instead of being held entirely in memory. Document access first checks workspace membership and the database record; object prefixes are not treated as authorization. `GET /api/v1/workspaces/{workspace_id}/documents/{document_id}/download` streams only an authorized document and does not expose storage keys or public object URLs. R2 is implemented but has not been live-tested against Cloudflare.

Local-to-R2 migration is a separate administrative command at `backend/scripts/migrate_local_documents_to_r2.py`. Dry-run is the default; apply and verify-only require a PostgreSQL database name confirmation. It reads document metadata from PostgreSQL, stages each local object in a bounded-memory spool while calculating SHA-256, conditionally creates its workspace-scoped R2 key, then downloads and verifies the destination checksum. It does not write database rows or chunks and never deletes local files. A JSON report is updated after each document and can be reused on restart. Existing matching objects are skipped after verification; corrupt objects are not overwritten. The active storage backend is not changed by the command.

Document ingestion and RAG are implemented. Token refresh/revocation, rate limiting, audit logging, analytics, and the production embeddable widget are not implemented.

Generation cancellation uses a coordinator selected by `GENERATION_COORDINATION_BACKEND`. The default `local` coordinator preserves single-process development only. Multi-instance and production deployments must configure `redis` plus backend-only `REDIS_URL`; production configuration rejects local coordination, and startup fails if Redis is unavailable. Each generation is registered in Redis with a unique generation ID, user ID, workspace ID, backend owner ID, lifecycle state, and expiring owner lease. The owner renews its lease and polls shared state while subscribed to a generation-specific Pub/Sub channel. A cancel request first validates the authenticated generation owner and workspace membership, then atomically marks shared state and publishes only the generation ID. Shared-state polling handles missed Pub/Sub notifications. The owner closes its provider stream and persists an interrupted assistant message. Atomic completion arbitration prevents a late cancel from changing an already-completing generation. State is removed after completion, cancellation or failure; Redis TTLs bound records after crashes. Redis loss causes active owners to cancel safely rather than continue without coordination. Redis is not used by unrelated application features.

Intended multi-tenant flow: authenticated client → rate limiting → server-derived identity and tenant authorization → conversation service → retrieval with tenant/document ACL filters → model provider → output policy checks → response with evidence.

Never trust a tenant ID supplied by a browser as proof of authorization. Enforce access in backend/database queries.
